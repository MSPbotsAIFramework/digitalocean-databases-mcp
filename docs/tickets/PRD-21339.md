## Product design

### Goals / Non-goals

**Goals (v1):**
- An agent holding a tenant's own DigitalOcean API token can, through this MCP server: discover and inspect that tenant's database clusters (and their replicas, databases, users, connection pools, firewall rules, backups, and engine config), create and resize clusters, add/remove logical databases and users, and manage the firewall's trusted-sources list.
- Every tool call is scoped to the credential presented on that single HTTP request; no credential or tenant data is cached, logged, or shared across requests (SOP §3 "three iron rules").
- Errors from the DigitalOcean API surface as the structured envelope (`not_configured` / `unauthorized` / `not_found` / `invalid_argument` / `rate_limited` / `upstream_error`) so the agent can branch on them instead of seeing a raw exception.

**Non-goals (v1 — deferred, see "Decisions made by DEV01" and §11 Risks):**
- Engine-specific sub-resources that only apply to one engine family: Kafka topics/schemas, OpenSearch indexes, MongoDB/Valkey-specific settings (eviction policy, SQL mode), online migration, autoscaling, logsinks, metrics-credentials rotation, region migration, major-version upgrade, read-replica promotion/creation, and PostgreSQL connection-pool create/delete.
- A UI. This is a backend-only MCP service; there is no MSPbots front-end surface to change.
- Provisioning DigitalOcean accounts or tokens for tenants — the tenant already has their own DigitalOcean account and self-generates the token (same self-service model already used for every other MSPbots connector).

### Acceptance criteria AC1..AC10

- **AC1**: Given a request to `POST /mcp` without the `X-DigitalOcean-Api-Key` header, When any tool is called, Then the server responds `401` listing the required header, and no call is made to the DigitalOcean API.
- **AC2**: Given a valid DigitalOcean API token in the header, When the agent calls `do_list_clusters`, Then the response lists every database cluster visible to that token (name, engine, version, status, region, size, num_nodes, tags, connection summary), and never includes a database user's password field.
- **AC3**: Given a cluster id, When `do_get_cluster` is called, Then the tool returns that cluster's full detail (connection / private_connection / standby_connection, maintenance window) and nothing belonging to a different cluster or a different token's account.
- **AC4**: Given the DigitalOcean API returns `429` for a request, When the tool retries, Then it backs off honoring the `Retry-After` header, and if still rate-limited after the retry budget, the tool returns `{"error":{"code":"rate_limited","retryable":true,...}}` rather than raising.
- **AC5**: Given a cluster id that does not exist (or does not belong to the caller's token), When any cluster-scoped tool is called with it, Then the tool returns `{"error":{"code":"not_found",...}}`, not a 500 or an unhandled exception.
- **AC6**: Given `do_create_cluster` is called with the required fields (name, engine, region, size), When the DigitalOcean API accepts the request, Then the tool returns the new cluster object with `status:"creating"`.
- **AC7**: Given `do_destroy_cluster` is called with an explicit `cluster_id`, When it executes, Then exactly that cluster is deleted; the tool has no name-pattern, tag-based, or "delete all" parameter — only a single explicit id is ever accepted (SOP §2.7).
- **AC8**: Given `do_update_firewall_rules` is called with a rule list, When it executes, Then the cluster's trusted-sources list becomes **exactly** that list (DigitalOcean replaces, not merges, on this endpoint) — and the tool description says so explicitly, so the agent does not assume an additive call.
- **AC9**: Given two concurrent requests carrying two different tenants' API tokens, When each calls any tool at the same time, Then each response reflects only the clusters/data reachable by its own token — no credential or response data crosses between the two requests (request-level isolation, SOP §3.3/§3.4).
- **AC10**: Given a `do_list_*` tool is called without an explicit `limit`, When the underlying account has more items than the default page size, Then the response is capped (default ≤ 50 items, hard max ≤ 200) and carries `has_more: true` instead of returning an unbounded list (SOP §2.5).

### Open questions

- [non-blocking] Should `do_destroy_cluster` and `do_remove_database`/`do_remove_user` require a tenant to have previously taken a backup, or otherwise add a confirmation step beyond "explicit id required"? — Defaulted to: no extra gate beyond SOP §2.7's "explicit id only, no fuzzy batch delete." DigitalOcean itself requires no confirmation token on these DELETE endpoints, and adding an MSPbots-side confirmation step would be a stateful workaround that conflicts with the "truly stateless" requirement (SOP §1.3). If product wants a stronger guard later (e.g., refuse destroy unless the ticket carries an explicit human-approved flag), that is a platform-level (gateway) concern, not something this vendor repo can enforce — see `mcp-track.md` §2.3 (reading the gateway code only to understand the call chain does not count as a change to it).
- [assumed] Whether tenants will primarily run PostgreSQL/MySQL/MongoDB (the three engines the v1 tool set treats generically) vs. Valkey/Kafka/OpenSearch (whose management surfaces are deferred, see Non-goals). Assumed PostgreSQL/MySQL/MongoDB are the common case based on DigitalOcean's own product positioning (these three are first-class "Managed Databases"; Valkey, Kafka, and OpenSearch are newer additions with narrower, engine-specific endpoint families). If this assumption is wrong, the "Follow-ups" list under Reuse & cleanup below is the plan for adding engine-specific tools in a follow-up ticket.

## Tech design

### Conclusion

Build a new Python 3.12 + uv + FastMCP service in `MSPbotsAIFramework/digitalocean-databases-mcp` from scratch (SOP main line A — there is nothing to reuse in this empty repo). It is a thin, stateless HTTP-to-REST translation layer: 18 tools wrapping DigitalOcean's public Databases REST API (`https://api.digitalocean.com/v2/databases/...`), with the caller's own bearer token read per-request from a single custom header and never persisted. This is the same shape as every other `<vendor>-mcp` repo in this org; no new architecture is introduced.

### Where the current implementation lives

Nothing — the repo has only a placeholder `README.md` at `1b998d0` (see Current state). The structure below follows the SOP §9 "recommended implementation" skeleton used by sibling repos in this org (e.g. the same `src/<vendor>_mcp/{config,api_client,server,tools/}.py` layout referenced in `vendor-mcp-development/reference/vendor-mcp-development-sop.md:363-386`).

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Thin REST wrapper (chosen) | One `httpx`-based `api_client.py` hitting DigitalOcean's documented REST endpoints directly; tools map 1:few onto endpoint groups | Matches the public, stable, well-documented REST API exactly; no extra moving parts; matches every sibling `<vendor>-mcp` repo's shape | None beyond normal implementation effort | Chosen |
| B. Use DigitalOcean's official `python-digitalocean` / `pydo` SDK | Less boilerplate for request construction | Saves some HTTP plumbing | Adds a third-party dependency whose version lifecycle we don't control, for a thin REST surface we could write directly in ~150 lines; SOP favors "reuse the repo's own patterns" over pulling in a wrapper SDK for a stable, simple REST API | Not chosen — the API is simple enough (bearer token, JSON, standard pagination) that a wrapper SDK buys little and adds a dependency to track |
| C. Cover the full 68-operation Databases surface in v1 | Mirror every endpoint 1:1 as a tool | Nothing left for a "v2" | Blows past SOP §2.1's ≤20 tool cap by 3x; most of the remaining 50 operations are engine-specific (Kafka/OpenSearch/Valkey) or rare lifecycle actions (region migration, major-version upgrade) that don't serve the common case | Not chosen — SOP explicitly says tools are capabilities, not endpoint mirrors; see Non-goals |

### Data & API contract

| Header | Required | Type | Meaning |
|---|---|---|---|
| `X-DigitalOcean-Api-Key` | yes | password | DigitalOcean personal access token (Control Panel → Account → API → Tokens). Forwarded as `Authorization: Bearer <token>` to `https://api.digitalocean.com`. Missing → `401` naming this header. |

| Tool | Hints | Maps to DigitalOcean endpoint |

**No database/migration**: this service is stateless and holds no persistent store of its own (SOP §1.3). **No MSPbots event bus involvement.** **Backward compatibility**: not applicable for a brand-new service; once registered, tool names/params become the contract (SOP §13) and any future rename/removal is a breaking change requiring prior notice.

### Key flow / sequence

```
Agent → Gateway (injects X-DigitalOcean-Api-Key from the tenant's stored credential)
      → POST /mcp  (digitalocean-databases-mcp)
          middleware: read header → ContextVar; 401 if missing
          tool handler: client_factory() → httpx.AsyncClient(base_url, Authorization: Bearer <token>)
          → GET/POST/PUT/DELETE https://api.digitalocean.com/v2/databases/...
          ← map status_code → {code, message, retryable} on error; else pass through trimmed JSON
      ← tool result (string)
      finally: ContextVar reset (credential discarded, nothing persisted)
```

### Non-functional

- **Idempotency & concurrency**: every tool call is a single outbound HTTP call to DigitalOcean; DigitalOcean itself is the source of truth for cluster state (e.g. `status: creating → online`), so this service does not need its own idempotency keys. One `httpx.AsyncClient` per request (not a shared module-level client holding one tenant's auth) — see SOP §3.4.
- **Performance**: list endpoints are paginated at the DigitalOcean side (`per_page` ≤ 200); this service caps its own default to 50 and hard-caps at 200 regardless of what the caller asks for (AC10). Connect timeout 5s / read timeout 30s; single tool call (incl. retries) bounded under 120s (SOP §5).
- **Security**: credential never logged, never written to disk, never cached across requests (SOP §3); `do_list_users` strips any field whose value looks like a stored database password before returning (DigitalOcean's user objects can include one depending on token scope) — this is a DEV01 decision, see below; `gitleaks detect` run before first commit to `main` and before every subsequent merge, per SOP §11.
- **Multi-tenant isolation**: there is no MSPbots-side tenant table here — isolation is per-HTTP-request, keyed off whichever DigitalOcean token the Gateway attaches to that request (SOP §3.3). Two tenants' requests hitting the same running container never share a `ContextVar` or cached client (AC9).
- **Observability**: structured JSON logs per request — tool name, truncated arg summary (cluster id ok to log, token/credential never), DigitalOcean path + status code, latency, error `code` if any (SOP §6). No request/response bodies logged verbatim (they can contain connection strings).

### Decisions made by DEV01

No one was available to ask (unattended design tick, generic ticket with no named capability — a non-blocking judgment call per `legs/design.md` S3/S4, not a product decision that would invalidate the whole design if guessed wrong). Choices made for this first version, each reversible in a follow-up ticket:

- **Tool prefix `do_` instead of the fuller `digitalocean_databases_`** — why: the repo and this MCP server are scoped to exactly one product (DigitalOcean Databases); `do_` is short, unambiguous within this single-purpose server, and keeps tool-name budget for descriptions. Alternative not chosen: `digitalocean_databases_<verb>_<resource>` (more explicit, but verbose and this org has no other DigitalOcean MCP to collide with).
- **Scope limited to PostgreSQL/MySQL/MongoDB-shaped operations (clusters, dbs, users, pools, firewall, backups, config, replicas); Kafka/OpenSearch/Valkey-specific endpoints deferred** — why: those three endpoint families only apply to specific engines, roughly double the tool count, and the ticket names no specific engine or capability. Alternative not chosen: cover all 68 operations in v1 — rejected, breaks SOP §2.1's ≤20 tool cap and most of those operations serve a narrow engine-specific audience.
- **`do_destroy_cluster` / `do_remove_database` / `do_remove_user` take only an explicit id, no confirmation flag, no "are you sure" round-trip** — why: SOP §2.7 requires explicit-id-only (no fuzzy batch delete) but does not require a confirmation step, and DigitalOcean's own API requires none; adding one would need session/state this service is explicitly forbidden from holding (SOP §1.3 "truly stateless"). Flagged `destructiveHint: true` so the calling agent's own policy layer can gate it.
- **`do_update_firewall_rules` is full-replace, not a merge/append tool, and marked destructive** — why: this mirrors DigitalOcean's own PUT semantics for this endpoint exactly (`databases_update_firewall_rules.yml`); building a client-side merge would require this stateless service to first `GET` the existing rules, compute a diff, and `PUT` the union — extra complexity and a race window between the two calls, for a safety property the description/AC can equally communicate. Agents must be told (and are, via the tool description and AC8) that this call replaces the whole list.
- **No DigitalOcean SDK dependency (`pydo` / `python-digitalocean`)** — why: the REST surface used here is simple (bearer token, standard JSON, standard pagination); a direct `httpx` wrapper is ~150 lines and keeps one fewer third-party dependency's release cadence to track. See Option analysis (Option B).
- **Password-shaped fields stripped from `do_list_users` / `do_get_cluster` responses** — why: DigitalOcean's database-user objects can carry a stored password when the token has the `database:view_credentials` scope; even though that scope is separate from "every action logged" risk on the MCP-gateway token itself, putting a raw DB password into an agent's context/transcript is an avoidable exposure for a read-only listing tool. Any tenant that specifically needs a user's password (e.g. to hand it to an app) can still see it in the DigitalOcean control panel; this server does not forward it. This is the only response-shaping decision made beyond token-economy trimming.

To change any of these, say so in a comment and move the ticket back to `5b - ready for groom`.

### Effort & breakdown

Story points: 3
Tier: cross-service flow / new subsystem boundary — row "3": a brand-new MCP service (not a modification), covering 9 DigitalOcean sub-resource groups across 18 tools, including 3 destructive write paths, with its own credential-isolation and error-mapping layer to build from zero.

Main uncertainty: whether DigitalOcean enforces any additional per-engine restriction (e.g. connection pools / backups only existing for Postgres and MySQL) that surfaces as more `not_found`-shaped edge cases than currently modeled — flagged in Risks below, not expected to change the point estimate.
Order inside this ticket: 1) scaffold + config + credential middleware + error envelope, 2) clusters.py (the tool group everything else depends on for ids), 3) databases.py + users.py, 4) network.py (pools/firewall) + ops.py (backups/config/replicas), 5) tests + README + Dockerfile, 6) merge, register, publish, wiki.

### Risks & dependencies

- **Engine-specific gaps surfacing as confusing `not_found`/empty results**: `do_list_connection_pools` and `do_list_backups` only apply to some engines (Postgres/MySQL); calling them against a MongoDB or Valkey cluster returns an empty list, not an error, per the DigitalOcean docs — tool descriptions say this explicitly so the agent doesn't read "empty" as "broken."
- **No test account during design/dev**: acceptable per SOP (lacking a vendor test account does not block publishing to INT); manual end-to-end verification is listed as "needs a real vendor account" and does not block merge, registration, or INT publish.
- **Dependency**: none on another ClickUp ticket or MSPbots repo. External dependency: DigitalOcean's public API and OpenAPI spec availability (both stable, versioned, in active use by DigitalOcean's own `doctl` CLI and official SDKs).
- **Follow-up scope creep risk**: the 50 deferred operations (Kafka/OpenSearch/Valkey/autoscaling/migration/etc., see Reuse & cleanup "Follow-ups") are real and will likely come back as future tickets once this v1 is in use — each should be scoped and estimated independently rather than bolted onto this one after the fact.

## Test cases

Full steps, preconditions, and evidence format live in the sibling `docs/tickets/PRD-21339.ac.json`. Pass/fail judgment statements:

- **TC1 · AC1**: Calling any tool over `POST /mcp` with the `X-DigitalOcean-Api-Key` header absent returns HTTP 401 and a body naming that header; no outbound call to `api.digitalocean.com` is made (verified via mock call count = 0).
- **TC2 · AC2**: `do_list_clusters` with a valid token returns a JSON array where every item has `id`/`name`/`engine`/`status`/`region` and no item contains a field named or shaped like a password.
- **TC3 · AC3**: `do_get_cluster` with a specific `cluster_id` returns only that cluster's object; calling it with a second token's `cluster_id` from the first token's credential returns `not_found`, not another tenant's data.
- **TC4 · AC4**: Mocking a `429` response with `Retry-After: 2` causes the client to wait and retry; if still `429` after the retry budget, the tool result is `{"error":{"code":"rate_limited","retryable":true}}`.
- **TC5 · AC5**: Any cluster-scoped tool called with a non-existent `cluster_id` returns `{"error":{"code":"not_found",...}}`, not a stack trace or 500.
- **TC6 · AC6**: `do_create_cluster` with required fields against a mocked `201` response returns an object whose `status` is `"creating"`.
- **TC7 · AC7**: `do_destroy_cluster`'s tool schema has exactly one required parameter (`cluster_id`, a string) and no array/filter/tag parameter that could match more than one cluster.
- **TC8 · AC8**: `do_update_firewall_rules` tool description explicitly states "replaces the entire trusted-sources list" (string-contains check in the `tools/list` snapshot test); a call with a 1-item list followed by a `do_list_firewall_rules` shows exactly 1 rule, not a union with whatever existed before.
- **TC9 · AC9**: Two concurrent mocked requests with different bearer tokens each see only their own mocked response; a shared-`ContextVar`-without-reset bug would make this test flaky/fail under `pytest-asyncio` concurrent execution.
- **TC10 · AC10**: `do_list_clusters` called with no `limit` against a mocked 75-item response returns at most 50 items and `has_more: true`; called with `limit=500` is clamped to 200.
- **TC11 · AC2, manual, needs a real vendor account**: Real DigitalOcean account with ≥1 cluster — `tools/list` then `tools/call do_list_clusters` over HTTP with a real token returns that account's actual cluster(s).
- **TC12 · AC6/AC7, manual, needs a real vendor account**: Real account — `do_create_cluster` (smallest size) then `do_destroy_cluster` on the same id round-trips cleanly against the live API (not just mocks).
- **TC13 · AC1, manual**: `curl -X POST .../mcp -H 'Accept: application/json, text/event-stream' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'` without the credential header returns 401 (confirms the Starlette middleware, not just a unit-test mock, enforces this).
- **TC14 · AC9, manual**: `curl -X POST .../mcp -H 'Accept: application/json, text/event-stream' -H 'X-DigitalOcean-Api-Key: <token>' -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'` returns `200` (not `400`), confirming `stateless_http=True` is actually wired (SOP §1.3 self-check).
